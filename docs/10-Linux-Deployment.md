# =============================================================================
# Daraban Platform — Linux Deployment Hardening & Monitoring (Task 8.4)
#
# This document is the comprehensive runbook for production deployments on
# Ubuntu LTS with Docker Compose v2. It covers:
#   - Nginx upstream with TLS 1.2/1.3 via Let's Encrypt (certbot)
#   - Observability stack (Prometheus + Grafana + alertmanager + Uptime Kuma)
#   - Backup/recovery procedures for Postgres (via pg_dump) and Redis (RDB+AOF)
#   - Security hardening (firewall, TLS strengthen, auth rate limiting)
#
# Prerequisites: a Linux host with Docker Engine + Docker Compose v2 installed,
# and this repository checked out to `/opt/daraban` (the same directory as the
# repo origin; CD workflow only changes DARABAN_TAG in the .env file, never repo
# contents).

## 1. System prerequisites

### 1.1 OS and Docker version
- Ubuntu LTS 22.04+ (tested on 22.04)
- Docker Engine 27+ (docker compose v2) — recommended via the official script:
  ```bash
  curl -fsSL https://get.docker.com | sh
  ```

### 1.2 User and group
- Create a dedicated deploy user (e.g. `ubuntu`, `deploy`, or `daraban`):
  ```bash
  sudo adduser --system --group --home /opt/daraban daraban
  sudo usermod -aG docker daraban
  ```
- SSH into the server as this user and run `docker version` / `docker compose ps` once.

### 1.3 SSH key for CI deploy
The CD pipeline uses `appleboy/ssh-action` from GitHub Actions with the
corresponding private key stored as the `DEPLOY_SSH_KEY` secret. Generate
and add it now:

```bash
ssh-keygen -t ed25519 -C "github-cd" -f /home/daraban/.ssh/id_ed25519_daraban -N ""
sudo bash -c 'mv /home/daraban/.ssh/id_ed25519_daraban.pub /home/daraban/.ssh/authorized_keys'
```

Now set the GitHub secret in your repo:
```bash
gh secret set DEPLOY_HOST  --body "$(ip addr show | grep 'inet ' | grep 'eth0\|ens\|enp' | head -1 | awk '{print $2}' | cut -d/ -f1)"
gh secret set DEPLOY_USER --body "daraban"
gh secret set DEPLOY_SSH_KEY < /home/daraban/.ssh/id_ed25519_daraban
```

> **Important**: The deploy user must own `/opt/daraban/.env` and the
> `DARABAN_TAG` line used during rolling updates (CD rewrites it). The same
> user must also be in the `docker` group.

## 2. Nginx production config (HTTPS + TLS + rate limiting + WebSocket)

### 2.1 Overview
- The **production Nginx configuration** lives at `deploy/nginx/nginx.prod.conf` and
  is mounted into the `daraban-nginx` container via the `docker-compose.prod.yml`
  overlay.
- The **dev** config (`docker/nginx.conf`) also gained auth rate limiting (`limit_req_zone` on `/api/v1/identity/auth/*`) and gzip in service of this task.
- TLS is terminated on Nginx; the 6 .NET services only ever see clean HTTPS.

### 2.2 Enable TLS on production
To move from the `docker-compose.yml` (HTTP:80 only) to HTTPS/443:

```bash
# 1. Switch to production overlay (if using cli deployment on server)
cd /opt/daraban
docker compose -f docker-compose.yml -f docker-compose.prod.yml pull
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d daraban-nginx

# 2. Validate that TLS is now listening on 443:
curl -ikv https://YOUR_DOMAIN

# 3. Generate or use an existing SSL certificate via Let's Encrypt (certbot + webroot):
#    a) Create a webroot temp directory and ensure it's excluded from being mounted
docker compose -f docker-compose.yml -f docker-compose.prod.yml exec nginx sh -c 'mkdir -p /var/www/certbot/.well-known/acme-challenge'
#    b) Run certbot in webroot mode (creates cert files inside the container unless you bind-mount a host dir)
docker compose -f docker-compose.yml -f docker-compose.prod.yml run --rm certbot renew --webroot -w /var/www/certbot/.well-known/acme-challenge -m your@email.com --agree-tos --keep-untaught-outdates

#    c) Mount cert files from the certbot directory to the nginx container (if you want persistence)
#    (Edit docker-compose.prod.yml to add this volume:
#       - ./ssl:/etc/letsencrypt:ro  # where ./ssl is generated by certbot)
```

### 2.3 Rate limiting on authentication endpoints
The production config applies a 5 requests per second burst of 10 on the
login/register URL family:

```nginx
limit_req_zone $binary_remote_addr zone=auth_rate_limit:10m rate=5r/s;

location /api/v1/identity/auth/login {
    limit_req zone=auth_rate_limit burst=10 nodelay;
    # ... existing auth config
}

location /api/v1/identity/auth/register {
    limit_req zone=auth_rate_limit burst=10 nodelay;
    # ... existing register config
}
```

### 2.4 WebSocket support for SignalR
All hubs (`/hubs/`) are correctly proxied with `Upgrade` headers via nginx.prod.conf:

```nginx
location /hubs/ {
    proxy_pass http://backend_api/hubs/;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
}
```

### 2.5 Gzip compression
Both nginx.conf and nginx.prod.conf have the standard gzip directives:

```nginx
gzip on;
gzip_vary on;
gzip_min_length 1024;
gzip_types text/plain text/css text/xml text/javascript
           application/json application/javascript application/rss+xml
           font/truetype font/opentype application/vnd.ms-fontobject
           image/svg+xml;
```

If you later enable a dev environment with real user traffic, verify compression
with `curl -H "Accept-Encoding: gzip" -s -D - ...`.

## 3. Observability stack (Prometheus + Grafana + alertmanager + Uptime Kuma)

### 3.1 Starting the monitoring stack
From your server:

```bash
cd /opt/daraban

# Activate observability (all services start on localhost only; nothing exposed publicly)
docker compose -f docker-compose.yml -f docker-compose.prod.yml -f docker-compose.observability.yml up -d

# Verify releases:
docker compose -f docker-compose.observability.yml ps
```

### 3.2 Accessing dashboards
- **Prometheus UI**: `http://127.0.0.1:9090` (only accessible from server)
- **Grafana UI**: `http://127.0.0.1:3000` — admin password is from `GRAFANA_ADMIN_PASSWORD`
  env var (default `admin`). First login:
  ```bash
  # Change the password from the UI or via environment variable (recommended to rotate)
  export GRAFANA_ADMIN_PASSWORD="$(openssl rand -base64 16)"
  docker compose -f docker-compose.observability.yml restart grafana
  ```
- **Uptime Kuma**: `http://127.0.0.1:3001` — monitors HTTP available endpoints. A typical
  uptime monitor entry point is `https://YOUR_DOMAIN/health/live` or `https://YOUR_DOMAIN/`
  (nginx will respond with 301 if only HTTP is configured). Pause any failures on first boot.

### 3.3 Alertmanager
Alertmanager is configured to route alerts to a webhook URL (add your own
product integration, data pipeline webhook, or email relay). Set
`ALERTMANAGER_WEBHOOK_URL` in your host environment (set it in
`DEPLOY_ENV` on deployment host, or simply `export ALERTMANAGER_WEBHOOK_URL="https://your-integration/webhook"` before running compose run):

```bash
export ALERTMANAGER_WEBHOOK_URL="https://your-log-shipper/webhook"
docker compose -f docker-compose.yml -f docker-compose.prod.yml -f docker-compose.observability.yml run --rm alertmanager ./alertmanager
```

By default the receiver is silent — adjust `deploy/monitoring/alertmanager.yml` to add your real webhook/email SMTP settings.

### 3.4 Scraping configuration
The Istock `/metrics` endpoint (HTTP + workers) is scraped by prometheus.yml for:
- all .NET services (hosts + workers) on their internal ports:
  - host-api:8080
  - host-agentapi:8081
  - worker-automation:9102
  - worker-notifications:9102
  - worker-reporting:9102
- exporters on localhost-only ports:
  - node-exporter:9100
  - postgres-exporter:9187
  - redis-exporter:9121

Within the compose network, all services resolve via DNS; nothing is exposed
to the public internet (all ports have `127.0.0.1:` bindings).

### 3.5 Grafana dashboards
The dashboard JSON at `deploy/monitoring/grafana/dashboards/daraban-health.json`
provides a basic set of panels:
- Request rate (HTTP requests per second overall)
- Error rate (HTTP errors per second)
- Queue depth (RabbitMQ messages pending for each worker)
- Memory (RSS memory usage per service)

Use Grafana's JSON import to load the dashboard, or add a similar built-in
panel as needed for your specific need.

### 3.6 Alert rules
There are 5 alert rules defined at `deploy/monitoring/rules.yml`:
- 5xx spike (error ceiling)
- Queue backup (messages_pending > threshold)
- Disk space (df -h usage < 15%)
- Memory pressure (memory RSS > 90%)
- Service health down (container not running)

You can preview rules before deploying to the alertmanager:

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d prometheus
docker compose -f docker-compose.yml -f docker-compose.prod.yml exec prometheus promtool check rules deploy/monitoring/rules.yml
```

## 4. Backup and recovery

### 4.1 Rotation policy
- Daily PostgreSQL dump (encrypted with openssl aes-256-cbc + pbkdf2)
- Retention: 7 daily + 4 weekly (Fridays only) + 12 monthly (1st-of-month only)
- Redis: already runs with RDB snapshots (`--save 900 1` and `--appendonly yes`);
  `backup.sh` runs `BGSAVE` each day to force a disk copy into the mounted
  redisdata volume once per day

The retention is implemented in `deploy/backup/backup.sh` via filename-based
prune (see pruning section in that script).

### 4.2 Setting up the backup script
From the server:

```bash
cd /opt/daraban
chmod +x deploy/backup/backup.sh deploy/backup/restore.sh deploy/backup/install-cron.sh

# Create log directory:
mkdir -p deploy/backup/logs
```

### 4.3 Daily automated backup (cron)
Run the install script once:

```bash
cd /opt/daraban
bash deploy/backup/install-cron.sh
```

This adds a cron line to `daraban` user crontab:

```cron
# Daily automatic backup (Daraban.Platform Task 8.4)
0 3 * * * /bin/bash deploy/backup/backup.sh >> deploy/backup/logs/backup_$(date +%Y%m%d).log 2>&1
```

- The backup runs at 03:00 UTC (your timezone can be adjusted by editing the line)
- The script encrypts the new `pg_dump` output with openssl and drops it into the
  encrypted backup directory.

### 4.4 Running the backup manually (for validation or on-changes)
```bash
cd /opt/daraban
bash deploy/backup/backup.sh
# If you want to test notification, also run alertmanager:
export ALERTMANAGER_WEBHOOK_URL="http://127.0.0.1:9093"
docker compose -f docker-compose.yml -f docker-compose.prod.yml -f docker-compose.observability.yml run --alertmanager
```

The plaintext decrypted dump occupies approx. <1% of available space for a new
daily backup (normally < 1GB database) and is cleaned up automatically after
5 minutes if you restarted the database container (see restore.sh cleanup).

### 4.5 Restoring a PostgreSQL backup
Restoring is a **manual one-time operation**; it does not run automatically to avoid accidental overwrites.

#### Step 1 — Deploy pass
The PostgreSQL backup must be decrypted with the production server's PostgreSQL
password. The script requires this via the environment variable, not from the
command line (security). On the server, you generate a file with the deployment password:

```bash
# PowerShell for Windows (useful if deploy user is simply running inside container)
$TARGET_PASS="$(ssh daraban@127.0.0.1 printenv CONNECTIONSTRINGS__Postgres | sed 's/.*Password=//' | tr -d '\r'); echo $TARGET_PASS > ~/.backup_pass"

# For a remote MongoDB-type sync-host, use scp to copy the backup to the server first:
scp admin@example.com:/backups/daraban_20240918_encrypted.dump ./backup.dump
```

#### Step 2 — Decrypt and drop into Postgres container
The `restore.sh` script now expects you to pass the backup file path:

```bash
docker compose exec -T host-api bash <<'EOF'
TARGET_PASS=$(printenv CONNECTIONSTRINGS__Postgres | sed 's/.*Password=//')
export BACKUP_PASS="$TARGET_PASS"

# Run decrypt + drop onto postgres (the container name must be daraban-postgres to avoid port issues)
bash deploy/backup/restore.sh ./backup.dump
EOF
```

When `restore.sh` finishes, examine the PostgreSQL container logs:

```bash
docker compose logs -f postgres
```

#### Step 3 — Verify integrity after restore
```bash
# List tables (to confirm Daraban modules are present):
docker compose exec postgres psql -U daraban -d daraban_platform -c "\dt"

# Run basic healthcheck:
curl https://YOUR_DOMAIN/health/live
```

If anything is missing or broken, answer configuration only; full migration automation is out of scope for this task.

## 5. Security hardening checklist

### 5.1 Nginx TLS configuration
The production nginx config enforces TLS 1.2 and 1.3:

```nginx
ssl_protocols TLSv1.2 TLSv1.3;
ssl_session_timeout 1d;
ssl_session_cache shared:MozSSL:10m;
ssl_session_tickets off;

ssl_ciphers 'ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384';

ssl_prefer_server_ciphers off;
```

Since `openssl genrsa -out certs/jwt-signing-key.pem 3072` uses RSA-3072,
you may add a stronger ecdsa cert later if you want to switch to ECDSA-only
ciphers.

### 5.2 Firewall (UFW or nftables)
Allow HTTPS and SSH only:

```bash
sudo ufw allow 22/tcp comment "SSH"
sudo ufw allow 443/tcp comment "Daraban HTTPS"
sudo ufw enable
# Verify
sudo ufw status numbered
```

### 5.3 Authentication rate limiting
Already configured on `/api/v1/identity/auth/login` and `/register` by the
limit_zone and limit_req directives in both nginx.conf and nginx.prod.conf.
Expected behavior: a sudden burst of brute-force login attempts will result
in 429 Too Many Requests from nginx before reaching the app.

### 5.4 Limiting exposure of /metrics
- `/metrics` is exported on each .NET service **inside the docker network only**.
- Nginx prod has no `location /metrics` block (consult nginx.prod.conf lines).
- The prometheus scraper reaches the containers via DNS (`host-api:8080`,
  etc.) and is only reachable from containers or the server itself (prometheus
  binds to `127.0.0.1:9090`).

By design, no public-facing ingress exposes `/metrics`.

### 5.5 Reducing attack surface
- Ensure `docker-compose.yml`, `docker-compose.prod.yml`, and `docker-compose.observability.yml`
  do not publish any admin ports (admin-console, mgmt and debug endpoints).
- In `docker-compose.prod.yml`, verify all services use `restart: unless-stopped` —
  containers always run as the current user (not root) inside the app containers.

### 5.6 User SSH access restrictions
- Your CI deploy user (fetched by appleboy/ssh-action) can only SSH to the
  host. Give them `moi` and `rsh` commands only (append the public key to
  `/home/deploy/.ssh/authorized_keys`). Test the login from your desktop with
  `ssh -i ~/.ssh/daraban_deploy -o StrictHostKeyChecking=no deploy@HOST`

## 6. CD pipeline integration (optional when TLS is built)

When you're ready to move from purely HTTPS-enabled repo-local may not have
real DNS. The CD deploy script expects the self-hosted NGINX_PORT env variable
to be read from the server:

In `deploy/backup/cron.sh` you use `export NGINX_PORT=80`. For the prod TLS run:

- Edit `docker-compose.prod.yml` to set `NGINX_PORT=443`.
- Invoke the deploy job when both the server and the GitHub workflow are
  configured:
  ```bash
  # In GitHub repo secret (but scheduler doesn't read secrets → use DEPLOY_ENABLED var):
  gh variable set DEPLOY_ENABLED --body true
  ```

Then the next push to master will attempt an **HTTPS-enabled rolling update**.
If there are SSL errors during attach steps (happens rarely with TLS 1.2/1.3), abort
the deploy job and handle next steps manually.

|---|---|---|
| **Log aggregation** (ELK/Loki) | Not requested; dev + CI logs are already captured via Serilog and Docker stdout | Loki + Grafana datasource + schema mapping for faster ops insights |

## 9. troubleshooting tips (real errors you may hit)

| Symptom | Likely cause | Fix |
|---|---|---|
| `sshd: internal error 0` or `Connection refused` on certbot DNS check | certbot's DNS check fails due to external firewall or port 80 not allowed | Allow port 80 traffic or configure certbot with validation/resolver options |
| `nginx: [emerg] "upstream" directive is duplicate` | Duplicate `upstream` definitions in other nginx config overlays (unlikely) | Inspect `deploy/nginx/nginx.prod.conf` by adding `vhost:server_name` mapping and checking includes |
| `::1:92` or IPv4 errors when inspecting trap | host networking uses IPv6 vs IPv4 mismatch | Use `$(cat deploy/nginx/.env | grep NGINX_PORT=)` instead of hard-coded; change to `8080` if your env is different |
| `BACKUP_PASS is not set` (restore.sh) | attempted to invoke script with BACKUP_PASS not exported | Use `docker compose exec -T host-api bash deploy/backup/restore.sh ./backup.dump` and let the script read credentials from the user crontab; check `whoami` and `cat env` before running restore |
| `cannot bind `/dev/main` or permission denied` on logs cleanup | some Linux systems have user-home device /dev/main blocked | Explicitly `touch ~/.backup_pass`; all dependencies are read-only, don't create intermediate files into /dev  |
| Prometheus scrapes return 404s | `/metrics` is not registered or the service is unpublished | Check that `PrometheusMetricsExtensions.MapDarabanMetrics()` is being called in each app's Program.cs; verify routing uses `app.MapMetrics()` |
| Grafana asks for admin password after login | changed GRAFANA_ADMIN_PASSWORD and didn't restart grafana container | `docker compose -f docker-compose.observability.yml restart grafana` |
